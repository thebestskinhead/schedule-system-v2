# 应用层逻辑修改点清单（决策已拍板 v2）

> 对应数据库 v2.1（`docs/数据库.md`）。每项列出「需求变更」（为什么）与「实现变更」（做什么），全部为自然语言描述。
> 标记：✓ = 已确认拍板；☐ = 待确认。
> 范围：Go 后端应用层 + 建表/脚本 SQL 同步。前端另列清单（涉及 `employment_status`、录入正式成员、删除注册页、expires_at NULL、批量离职操作）。

## 0. 已拍板决策（2026-08-17）

1. **值班统计口径**：排班均衡所需的「全历史有效班次数」由 `duty_records` 运行时聚合得出（口径：`status <> 'cancelled'`），无冗余列、无双源一致性问题（见 B）。
2. **`employment_status` 直换**：删除 `is_active`，API 直接返回 `employment_status`，前端同步改。
3. **离职语义**：离职 ≠ 删除——不能登录、**不能再次注册**（学号/邮箱在 users 表长期占用），用户管理的查重与列表 SQL 需覆盖全部状态。
4. **待入职（pending）密码占位**：默认 `bcrypt("123456")`（避免为空），**不可登录**，必须走激活流程完善信息后才可登录。
5. **手动录入无课表语义**：对「该用户、该时段」的现有无课表进行修改（增量），不做全量替换；仅 Excel 导入走全量替换。
6. **彻底删除公开注册**：现有 `Register` 接口/路由/页面/逻辑完全删除，杜绝外人注册。唯一入职途径 = 管理员「录入正式成员」→ 邀请邮件 → 激活。
7. **新增需求**：用户管理页面新增「录入正式成员」功能（见 H.2）。
8. **E 接受**：排班设置单例化 `config_key='global'`（见 E）。
9. **F 允许**：`expires_at` 允许 NULL（nil=永久），前端同步修改（见 F）。
10. **G 接受**：审批流原子化 `sp_advance_application`（见 G）。
11. **H4.1 接受且扩展**：离职支持**批量设置**——换届制下除晋升部长/副部外其余成员需集体离职（见 H.4.1）。
12. **H4.2 接受**：请假申请与联动（见 H.4.2）。
13. **I 接受**：事务收口 + `WithRetry`；**强调：所有涉及数据移动与删除的操作必须先备份**（见 I-1）。
14. **J 允许**：建表与脚本同步（见 J）。

## A. 用户三态化：`is_active` → `employment_status` ✓

| 确认 | 需求变更 | 实现变更 |
|---|---|---|
| ✓ | 账号状态升级三态 `pending/active/resigned`，`is_active` 删除，API 直接返回 `employment_status` | `model.User`：删 `IsActive`，新增 `EmploymentStatus`（常量 `pending/active/resigned`）；JSON 直接输出 `employment_status`，前端同步适配 |
| ✓ | 所有「只看在职」查询把 `is_active = 1` 换成 `employment_status = 'active'` | `dao/user.go` 全部查询（`GetByID/GetByStudentID/GetByEmail/List/GetUsersByIDs/ListByDepartment(s)/ListByFilter/GetByDeptRole/GetByDepartmentAndRole/GetByRole/Count`）、`dao/duty.go` 三个 JOIN、`dao/availability.go` 五个 JOIN 过滤条件统一替换 |
| ✓ | 「删除用户」语义改为「标记离职」 | `dao/user.go` 的 `Delete` 改为调用 `sp_mark_user_resigned`（不再 `UPDATE is_active=0`）；前端「删除用户」改为「离职」操作 |
| ✓ | 登录/扫码登录仅在职可登录 | `service/user.go` `Login` 与 `service/qr_login.go` 中 `!user.IsActive` 改为 `EmploymentStatus != 'active'` 拦截（pending 与 resigned 均不可登录） |
| ✓ | 离职不可再次注册；用户管理查重/列表 SQL 覆盖全部状态 | 录入/查重时：学号、邮箱在 users（含 pending/active/resigned）与 user_invitations 中均未占用；用户列表默认展示全状态并支持按状态筛选 |
| ✓ | **排班候选过滤：排除部门管理员与已离职/待入职** | `AvailabilityDAO.GetAvailableUsers/GetAvailableUsersForSchedule`（availability.go 3 处）保留 `dept_role != 'dept_admin'`，`is_active = 1` → `employment_status = 'active'`；`UserHandler.GetUsersForSchedule`（user.go）保留 `DeptRole == dept_admin` 跳过逻辑，其依赖的 `GetUserList/GetUserListByDepartment` 已按 `employment_status='active'` 过滤 |
| ✓ | 排班记录展示保留历史快照 | `duty.go` 三个 JOIN（`GetUsersByWeek/GetUsersByDepartment/GetByUserID`）仅替换过滤为 `employment_status='active'`（与现有 `is_active=1` 语义等价）；已排班的历史记录中若含已离职成员，其信息通过 JOIN 展示不受影响（若需显式保留离职者历史展示，另行确认展示口径） |

## B. 值班次数：`duty_records` 运行时聚合「有效班次」✓

| 确认 | 需求变更 | 实现变更 |
|---|---|---|
| ✓ | 排班均衡所需的「全历史有效班次数」不落冗余列，由 `duty_records` 运行时聚合（口径：status ≠ cancelled） | `dao/duty.go` `BatchCountByUsers` 改为 `SELECT user_id, COUNT(*) FROM duty_records WHERE user_id IN (?) AND status <> 'cancelled' GROUP BY user_id`（走索引 `idx_user_status`） |
| ✓ | 派生值不入库、不引入触发器，避免依赖 `log_bin_trust_function_creators` / SUPER 权限 | `duty_records` 是唯一数据源：任何影响排班的写入（排班确认/单格修改/单条状态推进/取消/请假批准/离职联动）都自然反映到聚合结果，无需逐路径维护 |

> 口径说明：排班均衡排序与过滤所需的计数口径统一为「有效班次」（status ≠ cancelled）；每人每周/每天的上限由本次排班的本地计数判定，不查当周库数据。
